# 2026-10-26｜記号・数字の形の違いや、崩れたJSONで止まらないようにする

公開版を使ったところ、「本文の欠落または形式の不備」で4回、「結果の形式を読み取れませんでした」で1回止まった。どれも、検品の中身ではなく、Geminiが返した形の小さな崩れで止まっていた。

## 本文の照合

- Geminiは区切った文を返すとき、記号や数字の形を変えることがある（全角数字→半角、「」→""、…→...、〜→~、①→1、半角カナ→全角、絵文字を落とすなど）。これまでは空白・全角半角・一部の絵文字の違いしか許していなかった。
- 照合を、文字（かな・漢字・英字）と数字だけで行うようにした。記号・空白・絵文字の違いでは止めない。
- 照合が通ったら、各区切りの本文を元の文章から切り出し直す。画面に出る本文は、常に貼った文章の文字そのまま。
- 文字や数字そのものが抜けた・入れ替わった場合は、これまで通り止める。メッセージを「Geminiが返した本文に文字の欠落があります」に分けた。

## 区分・指摘の名前のゆれ

- 「推測」→推論、「質問」→問い、「根拠のない断定」→根拠なき断定、「過剰な予測」→過剰な未来予測のように、よく出るゆれを正しい名前に直す。指摘が配列でなく文字列で返っても読む。
- 知らない区分が返っても止めず、小字を付けずに表示する。知らない指摘名は捨てる。

## JSONの読み取り

- 前後の説明文やコードフェンス、文字列の中の生の改行・タブ、不正なエスケープ（\' など）、末尾のカンマを直してから読む。
- 結果が長さの上限で途中で切れた場合は「文章が長く、Geminiの結果が途中で切れました。文章を分けて測ってください」と出す。安全上の理由で止まった場合も、その旨を出す。

## 確認

単体テストを6本足した（記号・数字・半角カナの違い、文字の入れ替わり、崩れたJSON、途中で切れた結果、安全上の停止、名前のゆれ）。全テストとブラウザのテストは通る。止まった5件の元の文章は手元にないため、その文章そのものでは確かめていない。

# 2026-10-26｜物差しを「AIの返答」と「文章全般」に分ける

これまでのよみときは、検品する文章をAIの返答と決めて測っていた。そのため、人が書いた文章を貼ると、書き手の体験までAIの作り話として扱うことがあった。Web上の文章にも使えるよう、物差しを二つに分けた。

## 物差しの切り替え

- 画面上部で「AIの返答」と「文章全般」を選ぶ。開いたときは「AIの返答」が選ばれている。
- 「測り直す」のすぐ上に「測定対象：AIの返答（変更する）」を表示する。「変更する」で上の切り替えへ戻れる。測っている間は押せない。
- 結果の上に「今回の検品：AIの返答／文章全般」と、その物差しで何を前提に測ったかを表示する。書き手をAIが判定した結果ではなく、利用者が選んだ設定の記録。
- 物差しを切り替えても入力した文章は残し、前の物差しで測った結果だけを消す。

## 文章全般の物差し

- 書き手が一人称で語る体験・見聞は事実（「事」）として扱い、外から確かめられないことだけを理由に咎めない。体験から全体への一般化、他人の理由や内心の言い切り、伝聞の事実化を検品する。
- 書き手の気持ち・不安・願望の表明は意見として扱い、それだけでは線を引かない。
- 根拠と限界を書き手自身が書いた推測は咎めない。語尾だけ弱めた推測は根拠不足として扱う。
- 書き換えでは、書き手の体験・主張・発話の目的を残し、指摘した部分だけを直す。意見を読者への質問に置き換えない。範囲を絞るときは限界を一文で書き添える。限界の一文は書き手の根拠の範囲だけを書き、世の中の傾向を否定も肯定もしない。
- 二周目では、指摘とは別に「書き手の言いたいことが残っているか」を確かめ、「保持／変更の疑い／判断できない」を表示する（新しい検出軸・点数ではない）。

## そのほか

- 体験・見聞を独立の区分にせず、「事」で示す。8つの軸は変わらない。
- Geminiが全角数字を半角にしたり絵文字を落としたりしただけで「本文の欠落」と止まらないようにした。文字そのものが抜けた場合は、これまで通り止める。
- temperature は0.2のまま。0と比べたが、0は見逃しの側に固まる例があった。

## 確認

Node.jsの単体テスト3本とChromiumでの画面テストは通る（APIは模擬）。文章全般の指示は、本物のGeminiで記録済みの例（三つ）を三回ずつ流して確かめた。

## 残っている課題

AIの返答の物差しでは、根拠なき断定や過剰肯定を拾った文を、書き換えで削るか相手への質問に置き換える決まりになっている。そのため、問題のある言い切りだけでなく、文の話題そのものが消えることがある。話題を残して言える範囲まで絞る形へ直す予定。

# 2026-09-18｜本文の代表色を分ける修正

## 基準にしたファイル

利用者が最後に渡した `yomitoki-public jintou.zip` の `yomitoki-public/index.html`。以前のZIPや公開サイトを基準に置き換えていない。元ファイルのハッシュは `source-manifest.json` に記録している。

## 確認した原因

この版には、すでにAPI出力の `primary` を本文色に使う実装がある。しかし、`primary` が「根拠なき断定」を指定した場合、あるいは有効な指定がない場合には、赤が代表色になる。後者では `FLAG_ORDER` の先頭が「根拠なき断定」だった。

実行画面からは `primary` の生の値は読めないため、今回の実行がどちらだったかは確定していない。一方で、画像に表示されていた「根拠なき断定＋過剰肯定」「根拠なき断定＋出どころなき引用」「根拠なき断定＋過剰な未来予測」を渡すと、この表示上の偏りを再現できた。

## 修正

`cleanFlags()` と `displayFlag()` を分離した。判定結果の `flags` と、本文で代表にする一色を別に扱う。

| 検出された指摘 | 本文の代表色 |
| --- | --- |
| 根拠なき断定＋過剰肯定 | 緑 |
| 根拠なき断定＋出どころなき引用 | 藍 |
| 根拠なき断定＋過剰な未来予測 | 琥珀 |
| 根拠なき断定のみ | 朱 |
| 具体区分が複数 | 有効な具体区分の `primary` を採用。なければAPIの返却順で一つ。 |

「根拠なき断定」より他の区分が重い・軽いという順位ではない。複数の指摘の中で、表示上より具体的な種類を代表にする方針。元の `flags`、本文、文区分、理由、書き換え案を変更しない。検出されていない区分を補って色数を増やす処理はない。

凡例にもこの表示ルールを記載した。表示結果を確認しやすいよう、各セグメントには `data-display-flag` が付く。

## 変えていないもの

- `CRITERIA`、`buildPrompt`、`buildRecheckPrompt` は元版と同一。検品・書き換えの指示は変更していない。
- Geminiの接続先・内部モデル名・生成設定・呼び出し回数は変更していない。
- 四色の色値、2pxの本文下線、赤い取り消し線、明朝見出し、方眼、朱印、ロゴは維持。
- 小字のクリック・キーボード操作は維持。
